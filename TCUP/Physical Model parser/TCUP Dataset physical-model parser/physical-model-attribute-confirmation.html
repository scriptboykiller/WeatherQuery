Physical Model 提取规则确认清单

用于确认：如何将 JSON、XML、JSON Schema、XML Schema（XSD）的树形业务结构， 转换为以点号连接的叶子属性路径。本文只讨论 Attribute Name / Attribute Path， 暂不讨论实际值、类型和约束输出。

目标模型 统一输出思想

JSON / XML / Schema
→
识别业务树形结构
→
叶子 Physical Model

示例：items[].price。路径本身是 Physical Model的唯一标识； 相同叶子名称出现在不同父节点下时，仍然是不同属性。

目前已经确认的规则

只输出叶子属性，不输出中间对象节点
路径分隔符固定使用 .
数组使用 []
JSON 不增加虚拟根节点
XML / XSD 保留真实根元素
当前不做 JSON 与 XML 的命名或结构归一化

需要确认的问题 带例子和建议

1

XML Attribute 如何表示？

需要区分 XML 标签属性和 XML 子元素，避免路径冲突。

P0 必须确认
输入 XML
<employee id="1001">
  <id>internal-id</id>
  <name>Dexter</name>
</employee>
建议输出
employee.@id
employee.id
employee.name
如果不使用 @，标签属性 id="1001" 与子元素 <id> 都会变成 employee.id，产生冲突。
建议：采用 employee.@id。
2

JSON 顶层是数组时，路径如何表示？

JSON 根节点不一定是 Object，也可能直接是 Array。

P0 必须确认
输入 JSON
[
  {"id": 1, "name": "A"},
  {"id": 2, "name": "B"}
]
候选输出
方案 A:
[].id
[].name

方案 B:
$[].id
$[].name
建议：使用 [].id，规则最简单。
3

空数组是否输出 Attribute？

实例数据中的空数组无法说明数组元素是简单值还是对象。

P0 必须确认
JSON 实例
{
  "owners": []
}
JSON Schema
{
  "properties": {
    "owners": {
      "type": "array",
      "items": {"type": "string"}
    }
  }
}
实例 JSON 只能确认 owners 是数组，但不能知道元素结构；Schema 可以确定它是字符串数组。
建议：实例输出 owners[]；如果将来需要子字段，则承认当前实例无法推断。
4

XML 单个重复元素，是否能判断为数组？

XML 实例只出现一次时，无法证明该元素可以重复。

P0 必须确认
XML 实例
<owners>
  <owner>team-a</owner>
</owners>
XSD 定义
<xs:element name="owner"
  type="xs:string"
  maxOccurs="unbounded"/>
只看实例可能得到 owners.owner；看 XSD 则明确得到 owners.owner[]。
建议：四种输入独立解析；允许 XML 实例与 XSD 对同一字段产生不同数组标记。
5

输出是否保持输入顺序？

顺序不影响路径唯一性，但会影响人工对照和测试结果稳定性。

P0 建议确认
输入
{
  "b": 1,
  "a": 2,
  "data": {"z": 3, "x": 4}
}
推荐输出
b
a
data.z
data.x
建议：默认保持输入顺序。
6

重复路径是否去重？

数组中多条记录会反复出现相同叶子属性。

P0 建议确认
输入 JSON
{
  "items": [
    {"id": 1},
    {"id": 2},
    {"id": 3}
  ]
}
推荐输出
items[].id
建议：按完整 Attribute Path 去重，同时保留第一次出现的位置顺序。
7

XML Namespace 是否进入路径？

XML 可能带前缀，同一个 local name 也可能属于不同命名空间。

P1 设计预留
输入 XML
<hr:employee xmlns:hr="urn:hr">
  <hr:name>Dexter</hr:name>
</hr:employee>
候选输出
方案 A:
employee.name

方案 B:
hr:employee.hr:name
一期建议：只取 local name，输出 employee.name；但设计上保留 namespace 信息，避免以后无法扩展。
8

JSON Schema 的 oneOf / anyOf / allOf 怎么处理？

复杂组合 Schema 可能定义多套互斥或合并结构。

P1 可暂缓
示例
{
  "oneOf": [
    {"properties": {"email": {"type":"string"}}},
    {"properties": {"phone": {"type":"string"}}}
  ]
}
可能结果
email
phone

但两者不会同时出现
如果简单合并，会失去“二选一”的语义；如果不合并，又可能漏掉 Attribute。
一期建议：明确标记为暂不支持，或只提取所有可能叶子路径但不表达组合关系。
9

动态属性名如何处理？

JSON Schema 可以允许任意 Key，因此无法生成固定 Attribute Name。

P1 可暂缓
示例 Schema
{
  "type": "object",
  "additionalProperties": {
    "type": "string"
  }
}
可能实例
{
  "teamA": "enabled",
  "teamB": "disabled"
}
一期建议：动态 Key 不生成固定 Physical Attribute；记录为 unsupported 或忽略。
10

Schema 引用支持到什么范围？

不解析引用可能丢失叶子属性，但完整支持跨文件引用会明显扩大范围。

P1 范围确认
JSON Schema 内部引用
{
  "properties": {
    "employee": {
      "$ref": "#/$defs/Employee"
    }
  }
}
XSD 外部引用
<xs:include
  schemaLocation="common-types.xsd"/>
建议：一期至少明确范围，不要默认承诺全部支持。
