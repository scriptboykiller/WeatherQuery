TTCUP · Transformation Mapping
MVP Design Proposal
Design proposal · Array + Object + OneOf

A focused design for turning repeated fieldValue entries into identifiable Physical Fields—without changing the database model.

Core decision
Support the Data Owner's oneOf-based Schema without changing the database or adding a Logical Field model. Use x-tcup-mapping to make the identifier and value explicit, then enhance the existing path and name.

01 · Why

The structure is visible.
The meaning is not.

Standard parsing sees repeated array elements with the same fieldValue. The actual business meaning is carried by fieldName.const inside each oneOf branch.

02 · Contract

The Data Owner declares meaning.
TCUP does not guess.

A small Schema extension tells TCUP which properties identify an array element and which property contains the value to map.

Example A · Single Identifier
{
  "oneOf": [
    { "properties": {
      "fieldName": {
        "const": "PREV_ACTOR_LATE_RESPONSE_CODE"
      },
      "fieldValue": { "type": "string" }
    } },
    { "properties": {
      "fieldName": {
        "const": "PREV_ACTOR_ESCALATION"
      },
      "fieldValue": { "type": "string" }
    } }
  ],
  "x-tcup-mapping": {
    "identifier": ["fieldName"],
    "valueProperty": "fieldValue"
  }
}
Example B · Composite Identifier
{
  "oneOf": [
    { "properties": {
      "fieldName": { "const": "COMMENT" },
      "fieldType": { "const": "SUPERVISORY" },
      "fieldValue": { "type": "string" }
    } },
    { "properties": {
      "fieldName": { "const": "COMMENT" },
      "fieldType": { "const": "REVIEWER" },
      "fieldValue": { "type": "string" }
    } }
  ],
  "x-tcup-mapping": {
    "identifier": ["fieldName", "fieldType"],
    "valueProperty": "fieldValue"
    }
}
A

oneOf defines candidate business fields

Each branch represents one identifiable type of array element.

B

const provides the exact identifier value

TCUP reads explicit values only; it never infers them from names or descriptions.

C

identifier specifies the identifying properties

One property or multiple properties can be used together.

D

valueProperty specifies the mapping target

It identifies the value node that TCUP should expose.

05 · Identifiers

One consistent rule
for single or composite identifiers

The syntax stays minimal and predictable: one identifier creates one condition; multiple identifiers are joined with &&, and names follow the declaration order in the Schema.

Single Identifier

Common case
identifier: ["fieldName"]
↓
stateFormData[@fieldName='PREV_ACTOR_ESCALATION'].fieldValue fieldValue(PREV_ACTOR_ESCALATION)

Composite Identifier

Extensible
identifier: ["fieldName", "fieldType"]
↓
stateFormData[@fieldName='comment' && @fieldType='SUPERVISORY'].fieldValue fieldValue(comment | SUPERVISORY)

06 · Value

Why this is the right
MVP approach

The change stays within parsing and naming logic. It does not expand the data model or affect existing behavior for standard Schemas.

01

Small implementation footprint

Reuse the existing Physical Model name and field path strings with zero database migration.

02

Precise representation

The Path expresses both the real physical array and its filter condition without pretending it is a regular object.

03

Clear user experience

04

Data Owner controlled

The Data Owner Schema explicitly declares mapping semantics; TCUP avoids unreliable field guessing.

05

Backward compatible

Objects, arrays, and fields without x-tcup-mapping continue through the existing parsing logic.

06

Naturally extensible

The same contract supports single and composite identifiers without another model change.

07 · Boundaries

Clear boundaries.
No “smart guessing.”

The MVP prioritizes predictable behavior. Enhanced logic is enabled only when the Schema satisfies the explicit contract; otherwise TCUP safely falls back to existing behavior.

Rules and Guardrails

  • Enable the enhancement only for target arrays containing x-tcup-mapping.
  • Every identifier must have a const in its corresponding oneOf branch.
  • valueProperty must reference a property that exists in the branch.
  • Use the fixed condition syntax @property='value'; join composite conditions with &&.
  • If the contract is missing or invalid—or the Schema is standard—use existing parsing logic and do not guess.
